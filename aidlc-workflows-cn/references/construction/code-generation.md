# 代码生成 - 详细步骤

## 概述
本阶段通过两个集成部分为每个工作单元生成代码：
- **第 1 部分 - 规划**：创建带有明确步骤的详细代码生成计划
- **第 2 部分 - 生成**：执行已批准的计划以生成代码、测试和制品

**注意**：对于 Brownfield 项目，"生成"意味着在适当时修改现有文件，而不是创建重复文件。

## 前置条件
- 该单元的设计生成必须已完成
- NFR 实现（如执行）必须已完成
- 所有单元设计制品必须可用
- 单元已准备好进行代码生成

# 第 1 部分：规划

## 第 1 步：分析单元上下文
- [ ] 阅读设计生成阶段产生的单元设计制品
- [ ] 阅读单元故事地图以了解分配的故事
- [ ] 识别单元依赖关系和接口
- [ ] 验证单元已准备好进行代码生成

## 第 2 步：创建详细的单元代码生成计划
- [ ] 从 `aidlc-docs/aidlc-state.md` 读取工作区根目录和项目类型
- [ ] 确定代码位置（结构模式见关键规则）
- [ ] **仅 Brownfield**：审阅逆向工程得到的 code-structure.md，了解要修改的现有文件
- [ ] 记录确切的路径（绝不使用 aidlc-docs/）
- [ ] 为单元生成创建明确的步骤：
  - 项目结构搭建（仅 Greenfield）
  - 业务逻辑生成
  - 业务逻辑单元测试
  - 业务逻辑总结
  - API 层生成
  - API 层单元测试
  - API 层总结
  - Repository 层生成
  - Repository 层单元测试
  - Repository 层总结
  - 前端组件生成（如适用）
  - 前端组件单元测试（如适用）
  - 前端组件总结（如适用）
  - 数据库迁移脚本（如果存在数据模型）
  - 文档生成（API 文档、README 更新）
  - 部署制品生成
- [ ] 按顺序为每个步骤编号
- [ ] 包含故事映射引用
- [ ] 为每个步骤添加复选框 [ ]

## 第 3 步：包含单元生成上下文
- [ ] 对于该单元，包含：
  - 该单元实现的故事
  - 对其他单元/服务的依赖
  - 预期的接口和契约
  - 该单元拥有的数据库实体
  - 服务边界和职责

## 第 4 步：创建单元计划文档
- [ ] 将完整计划保存为 `aidlc-docs/construction/plans/{unit-name}-code-generation-plan.md`
- [ ] 包含步骤编号（第 1 步、第 2 步等）
- [ ] 包含单元上下文和依赖关系
- [ ] 包含故事可追溯性
- [ ] 确保计划可逐步执行
- [ ] 强调该计划是代码生成的唯一事实来源

## 第 5 步：总结单元计划
- [ ] 向用户提供单元代码生成计划的摘要
- [ ] 突出单元生成方法
- [ ] 解释步骤顺序和故事覆盖范围
- [ ] 注明步骤总数和预估范围

## 第 6 步：记录审批提示
- [ ] 在请求审批之前，在 `aidlc-docs/audit.md` 中记录带有时间戳的提示
- [ ] 包含对完整单元代码生成计划的引用
- [ ] 使用 ISO 8601 时间戳格式

## 第 7 步：等待明确审批
- [ ] 在用户明确批准单元代码生成计划之前不要继续
- [ ] 审批必须涵盖整个计划和生成顺序
- [ ] 如果用户请求更改，更新计划并重复审批流程

## 第 8 步：记录审批响应
- [ ] 在 `aidlc-docs/audit.md` 中记录用户带有时间戳的审批响应
- [ ] 包含用户响应的确切文本
- [ ] 明确标记审批状态

## 第 9 步：更新进度
- [ ] 在 `aidlc-state.md` 中将代码生成第 1 部分（规划）标记为完成
- [ ] 更新"当前状态"部分
- [ ] 为过渡到代码生成做准备

# 第 2 部分：生成

## 第 10 步：加载单元代码生成计划
- [ ] 从 `aidlc-docs/construction/plans/{unit-name}-code-generation-plan.md` 读取完整计划
- [ ] 识别下一个未完成的步骤（第一个 [ ] 复选框）
- [ ] 加载该步骤的上下文（单元、依赖、故事）

## 第 11 步：执行当前步骤
- [ ] 验证计划中的目标目录（绝不使用 aidlc-docs/）
- [ ] **仅 Brownfield**：检查目标文件是否存在
- [ ] 精确生成当前步骤描述的内容：
  - **如果文件存在**：就地修改（绝不创建 `ClassName_modified.java`、`ClassName_new.java` 等）
  - **如果文件不存在**：创建新文件
- [ ] 写入正确位置：
  - **应用程序代码**：按项目结构写入工作区根目录
  - **文档**：`aidlc-docs/construction/{unit-name}/code/`（仅 markdown）
  - **构建/配置文件**：工作区根目录
- [ ] 遵循单元故事需求
- [ ] 尊重依赖关系和接口

## 第 12 步：更新进度
- [ ] 在单元代码生成计划中将已完成的步骤标记为 [x]
- [ ] 当相关单元故事的生成完成时，将其标记为 [x]
- [ ] 更新 `aidlc-docs/aidlc-state.md` 的当前状态
- [ ] **仅 Brownfield**：验证未创建重复文件（例如，没有 `ClassName_modified.java` 与 `ClassName.java` 并存）
- [ ] 保存所有生成的制品

## 第 13 步：继续或完成生成
- [ ] 如果还有更多步骤，返回第 10 步
- [ ] 如果所有步骤都完成，继续呈现完成消息

## 第 14 步：呈现完成消息
- 按以下结构呈现完成消息：
     1. **完成公告**（必需）：始终以此开头：

```markdown
# 💻 Code Generation Complete - [unit-name]
```

     2. **AI 摘要**（可选）：提供结构化的要点摘要
        - **Brownfield**：区分修改的文件与创建的文件（例如，"• 修改：`src/services/user-service.ts`"，"• 创建：`src/services/auth-service.ts`"）
        - **Greenfield**：列出带路径的已创建文件（例如，"• 创建：`src/services/user-service.ts`"）
        - 列出带路径的测试、文档、部署制品
        - 保持事实性，不包含工作流指令
     3. **格式化工作流消息**（必需）：始终以此精确格式结尾：

```markdown
> **📋 <u>**REVIEW REQUIRED:**</u>**  
> Please examine the generated code at:
> - **Application Code**: `[actual-workspace-path]`
> - **Documentation**: `aidlc-docs/construction/[unit-name]/code/`



> **🚀 <u>**WHAT'S NEXT?**</u>**
>
> **You may:**
>
> 🔧 **Request Changes** - Ask for modifications to the generated code based on your review  
> ✅ **Continue to Next Stage** - Approve code generation and proceed to **[next-unit/Build & Test]**

---
```

## 第 15 步：等待明确审批
- 在用户明确批准生成的代码之前不要继续
- 审批必须清晰明确
- 如果用户请求更改，更新代码并重复审批流程

## 第 16 步：记录审批并更新进度
- 在 audit.md 中记录带有时间戳的审批
- 记录用户带有时间戳的审批响应
- 在 aidlc-state.md 中将该单元的代码生成阶段标记为完成

## 关键规则

### 代码位置规则
- **应用程序代码**：仅工作区根目录（绝不使用 aidlc-docs/）
- **文档**：仅 aidlc-docs/（markdown 摘要）
- **在生成代码之前**从 aidlc-state.md 读取工作区根目录

**按项目类型的结构模式**：
- **Brownfield**：使用现有结构（例如，`src/main/java/`、`lib/`、`pkg/`）
- **Greenfield 单单元**：工作区根目录下的 `src/`、`tests/`、`config/`
- **Greenfield 多单元（微服务）**：`{unit-name}/src/`、`{unit-name}/tests/`
- **Greenfield 多单元（单体）**：`src/{unit-name}/`、`tests/{unit-name}/`

### Brownfield 文件修改规则
- 在生成前检查文件是否存在
- 如果存在：就地修改（绝不创建 `ClassName_modified.java` 之类的副本）
- 如果不存在：创建新文件
- 生成后验证没有重复文件（第 12 步）

### 规划阶段规则
- 为所有生成活动创建明确、编号的步骤
- 在计划中包含故事可追溯性
- 记录单元上下文和依赖关系
- 在生成前获得用户的明确审批

### 生成阶段规则
- **无硬编码逻辑**：只执行单元计划中写的内容
- **严格遵循计划**：不要偏离步骤顺序
- **更新复选框**：完成每个步骤后立即标记 [x]
- **故事可追溯性**：功能实现后标记单元故事 [x]
- **尊重依赖**：仅在单元依赖满足时实施

### 自动化友好代码规则
生成 UI 代码（Web、移动、桌面）时，确保元素对自动化友好：
- 为交互元素（按钮、输入框、链接、表单）添加 `data-testid` 属性
- 使用一致的命名：`{component}-{element-role}`（例如，`login-form-submit-button`、`user-list-search-input`）
- 避免在渲染之间变化的动态或自动生成的 ID
- 在代码更改期间保持 `data-testid` 值稳定（仅当元素用途改变时才更改）

## 完成标准
- 创建并批准完整的单元代码生成计划
- 单元代码生成计划中的所有步骤标记为 [x]
- 所有单元故事按计划实现
- 所有代码和测试已生成（测试将在构建与测试阶段执行）
- 部署制品已生成
- 完整单元已准备好进行构建和验证
