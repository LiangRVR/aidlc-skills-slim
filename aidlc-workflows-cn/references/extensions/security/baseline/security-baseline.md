# 基线安全规则

## 概述
这些安全规则是适用于所有 AI-DLC 阶段的强制性（MANDATORY）横切约束。它们不是可选建议 —— 而是在生成问题、产出设计制品、生成代码和呈现完成消息时，各阶段必须强制执行的硬性约束。

**强制执行（Enforcement）**：在每个适用阶段，模型在向用户呈现阶段完成消息之前，必须核验是否符合这些规则。

### 阻断性安全发现行为
**阻断性安全发现（blocking security finding）** 意味着：
1. 该发现必须在阶段完成消息的 "Security Findings" 部分下列出，并附上 SECURITY 规则编号和描述
2. 在所有阻断性发现解决之前，阶段不得提供 "Continue to Next Stage"（继续到下一阶段）选项
3. 模型只能提供 "Request Changes"（请求变更）选项，并清楚说明需要变更的内容
4. 该发现必须记录到 `aidlc-docs/audit.md` 中，并附上 SECURITY 规则编号、描述和阶段上下文

如果某条 SECURITY 规则不适用于当前项目（例如不存在数据存储时的 SECURITY-01），请在合规性摘要中将其标记为 **N/A** —— 这不属于阻断性发现。

### 默认强制执行
本文档中的所有规则默认都是**阻断性**的。如果任何规则的核验标准未满足，即为阻断性安全发现 —— 请遵循上述阻断性发现行为。

### 核验标准格式
本文档中的核验项是描述合规性检查的普通要点，不同于阶段计划文件中用于进度跟踪的 `- [ ]` / `- [x]` 复选框。审查期间，每个条目都应评估为合规或不合规。

## 规则 SECURITY-01：静态与传输中加密

**规则**：每个数据持久化存储（数据库、对象存储、文件系统、缓存或任何等效设施）都必须具备：
- 使用托管密钥服务或客户管理密钥启用静态加密（encryption at rest）
- 强制传输中加密（encryption in transit，所有进出存储的数据移动使用 TLS 1.2+）

**核验**：
- 不存在未定义加密配置块的存储资源
- 不存在使用未加密协议的数据库连接字符串
- 对象存储通过策略强制静态加密并拒绝非 TLS 请求
- 数据库实例启用存储加密并强制 TLS 连接

---

## 规则 SECURITY-02：网络中间设备的访问日志

**规则**：每个处理外部流量的面向网络的中间设备都必须启用访问日志。这包括：
- 负载均衡器 → 访问日志写入持久化存储
- API 网关 → 执行日志和访问日志写入集中式日志服务
- CDN 分发 → 标准日志或实时日志

**核验**：
- 不存在未启用访问日志的负载均衡器资源
- 不存在未配置访问日志的 API 网关阶段
- 不存在未配置日志记录的 CDN 分发

---

## 规则 SECURITY-03：应用级日志记录

**规则**：每个已部署的应用组件都必须包含结构化日志基础设施：
- 必须配置日志框架
- 日志输出必须导向集中式日志服务
- 日志必须包含：时间戳、关联/请求 ID、日志级别和消息
- 敏感数据（密码、令牌、PII）不得出现在日志输出中

**核验**：
- 每个服务/函数入口点都包含已配置的日志记录器
- 生产代码中没有将临时日志语句作为主要日志记录机制
- 日志配置将输出路由到集中式日志服务
- 不会记录任何机密、令牌或 PII

---

## 规则 SECURITY-04：Web 应用的 HTTP 安全响应头

**规则**：以下 HTTP 响应头必须在所有提供 HTML 的端点上设置：

| Header | Required Value |
|---|---|
| `Content-Security-Policy` | Define a restrictive policy (at minimum: `default-src 'self'`) |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` |
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` | `DENY` (or `SAMEORIGIN` if framing is required) |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |

**注意**：`X-XSS-Protection` 在现代浏览器中已废弃。请改用 `Content-Security-Policy`。

**核验**：
- 中间件或响应拦截器设置所有必需的响应头
- CSP 策略在没有记录理由的情况下不使用 `unsafe-inline` 或 `unsafe-eval`
- HSTS max-age 至少为 31536000（1 年）

---

## 规则 SECURITY-05：所有 API 参数的输入验证

**规则**：每个 API 端点（REST、GraphQL、gRPC、WebSocket）都必须在处理之前验证所有输入参数。验证必须包括：
- **类型检查**：拒绝意外的类型
- **长度/大小边界**：对字符串强制执行最大长度，对数组和载荷强制执行最大大小
- **格式验证**：对结构化输入（电子邮件、日期、ID）使用白名单（正则表达式或 schema）
- **净化处理**：转义或拒绝用户提供的字符串中的 HTML/脚本内容以防止 XSS
- **注入防护**：所有数据库操作使用参数化查询（绝不使用字符串拼接）

**核验**：
- 每个 API 处理器都使用验证库或 schema
- 没有将原始用户输入拼接进 SQL、NoSQL 或 OS 命令
- 字符串输入有明确的最大长度约束
- 在框架或网关层面配置了请求体大小限制

---

## 规则 SECURITY-06：最小权限访问策略

**规则**：每个身份和访问管理策略、角色或权限边界都必须遵循最小权限原则：
- 使用特定的资源标识符 —— 除非 API 不支持资源级权限（记录该例外），否则绝不使用通配符资源
- 使用特定的操作 —— 绝不使用通配符操作
- 在可能的情况下限定条件范围
- 将读写权限拆分为不同的策略语句

**核验**：
- 没有策略包含通配符操作或通配符资源而没有记录的例外
- 没有服务角色拥有超出其实际调用范围更广的权限
- 在可能的情况下避免内联策略，优先使用托管策略
- 每个角色都有限定到特定服务或账户的信任策略

---

## 规则 SECURITY-07：限制性网络配置

**规则**：所有网络配置（安全组、网络 ACL、路由表）都必须遵循默认拒绝（deny-by-default）：
- 防火墙规则：只开放应用所需的特定端口
- 除面向公众的负载均衡器在 80/443 端口外，不允许源为 `0.0.0.0/0` 的入站规则
- 不允许在所有端口上使用 `0.0.0.0/0` 的出站规则，除非有明确理由
- 私有子网不得有直接指向互联网网关的路由
- 在可用的情况下，对云服务访问使用私有端点

**核验**：
- 没有防火墙规则允许在公开负载均衡器上除 80/443 之外的任何端口上的入站 `0.0.0.0/0`
- 数据库和应用防火墙规则将源限制为特定的 CIDR 块或安全组引用
- 私有子网通过 NAT 网关（而非互联网网关）路由
- 对高流量云服务调用使用私有端点

---

## 规则 SECURITY-08：应用级访问控制

**规则**：每个访问或修改资源的应用端点都必须在应用层强制授权检查：
- **默认拒绝**：除非明确标记为公开，否则所有路由/端点都必须要求身份认证
- **对象级授权**：每个通过 ID 引用资源的请求都必须验证请求用户/主体拥有该资源或有权访问该资源（防止 IDOR）
- **功能级授权**：管理或特权操作必须在服务端检查调用者的角色/权限 —— 绝不依赖客户端隐藏
- **CORS 策略**：跨源资源共享必须限制为明确允许的来源 —— 绝不在已认证端点上使用 `Access-Control-Allow-Origin: *`
- **令牌验证**：JWT 或会话令牌必须在每个请求上于服务端进行验证（签名、过期时间、受众、颁发者）

**核验**：
- 每个控制器/处理器都应用了授权中间件或守卫
- 没有端点在未验证调用者所有权或权限的情况下返回资源 ID 的数据
- 管理/特权路由在服务端强制执行明确的角色检查
- CORS 配置在已认证端点上不使用通配符来源
- 令牌验证在每个请求上于服务端进行（不仅限于登录时）

---

## 规则 SECURITY-09：安全加固与错误配置防护

**规则**：所有已部署组件都必须遵循加固基线：
- **无默认凭据**：部署前必须更改或禁用默认用户名/密码
- **最小化安装**：移除或禁用未使用的功能、框架、示例应用和文档端点
- **错误处理**：生产环境错误响应不得向最终用户暴露堆栈跟踪、内部路径、框架版本或数据库详细信息
- **目录列表**：Web 服务器必须禁用目录列表
- **云存储**：除非明确需要并记录，否则云对象存储必须阻止公开访问
- **补丁管理**：运行时环境、框架和操作系统镜像必须使用当前受支持的版本

**核验**：
- 配置文件、环境变量或 IaC 模板中不存在默认凭据
- 生产环境的错误响应返回通用消息（无堆栈跟踪或内部详细信息）
- 云对象存储已阻止公开访问，除非存在记录的例外
- 未部署示例/演示应用或默认页面
- 框架和运行时版本是当前且受支持的

---

## 规则 SECURITY-10：软件供应链安全

**规则**：每个项目都必须管理其软件供应链：
- **依赖固定（pinning）**：所有依赖必须使用精确版本或锁文件
- **漏洞扫描**：必须配置依赖漏洞扫描器
- **无未使用的依赖**：移除未实际使用的软件包
- **仅可信来源**：依赖必须从官方注册表或经过验证的私有注册表获取 —— 不从未经验证的第三方来源获取
- **SBOM**：项目必须为生产部署生成软件物料清单（Software Bill of Materials）
- **CI/CD 完整性**：构建流水线必须使用固定的工具版本和经过验证的基础镜像 —— 生产环境的 Dockerfile 或 CI 配置中不得使用 `latest` 标签

**核验**：
- 存在锁文件并已提交到版本控制
- CI/CD 中包含依赖漏洞扫描步骤，或在构建说明中记录
- 未包含未使用或已废弃的依赖
- Dockerfile 和 CI 配置在生产环境中不使用 `latest` 或未固定的镜像标签
- 依赖来自官方或经过验证的注册表

## 规则 SECURITY-11：安全设计原则

**规则**：应用设计必须从一开始就纳入安全：
- **关注点分离**：安全关键逻辑（身份认证、授权、支付处理）必须隔离在专用模块中 —— 不得分散在代码库各处
- **纵深防御**：不应让单一控制成为唯一的防线 —— 分层控制（验证 + 授权 + 加密）
- **速率限制**：面向公众的端点必须实现速率限制或节流以防止滥用
- **业务逻辑滥用**：设计必须考虑误用场景 —— 而不只是正常路径场景

**核验**：
- 安全关键逻辑封装在专用模块或服务中
- 在面向公众的 API 上配置了速率限制
- 设计文档至少涵盖一个误用/滥用场景

---

## 规则 SECURITY-12：身份认证与凭据管理

**规则**：每个具有用户身份认证的应用都必须实现：
- **密码策略**：最少 8 个字符，并对照已泄露密码列表进行检查
- **凭据存储**：密码必须使用自适应算法进行哈希 —— 绝不使用弱哈希或非自适应哈希
- **多因素身份验证**：管理账户必须（MUST）支持 MFA，并且所有用户应该（SHOULD）可以使用 MFA
- **会话管理**：会话必须有服务端过期时间、登出时失效，并使用 secure/httpOnly/sameSite cookie 属性
- **暴力破解防护**：登录端点必须在多次失败后实现账户锁定、渐进式延迟或 CAPTCHA
- **无硬编码凭据**：源代码或 IaC 模板中不得包含密码、API 密钥或机密 —— 使用机密管理器

**核验**：
- 密码哈希使用自适应算法（不是弱哈希或非自适应哈希）
- 会话 cookie 设置 `Secure`、`HttpOnly` 和 `SameSite` 属性
- 登录端点具有暴力破解防护（锁定、延迟或 CAPTCHA）
- 源代码或配置文件中没有硬编码凭据
- 管理账户支持 MFA
- 会话在登出时失效并具有定义的过期时间

---

## 规则 SECURITY-13：软件与数据完整性验证

**规则**：系统必须验证软件和数据的完整性：
- **反序列化安全**：未经验证的不可信数据不得反序列化 —— 使用安全的反序列化库或允许类型的白名单
- **制品完整性**：下载的依赖、插件和更新必须通过校验和或数字签名进行验证
- **CI/CD 流水线安全**：构建流水线必须限制谁能修改流水线定义 —— 在代码作者和部署审批者之间分离职责
- **CDN 和外部资源**：从外部 CDN 加载的脚本或资源必须使用子资源完整性（Subresource Integrity，SRI）哈希
- **数据完整性**：关键数据修改必须可审计（谁在何时更改了什么）

**核验**：
- 没有对不可信输入进行不安全的反序列化
- 从 CDN 加载的外部脚本包含 SRI 完整性属性
- CI/CD 流水线定义受到访问控制，且变更可审计
- 关键数据变更记录行为者、时间戳以及变更前/后的值

---

## 规则 SECURITY-14：告警与监控

**规则**：除日志记录（SECURITY-02、SECURITY-03）之外，系统还必须包括：
- **安全事件告警**：必须为高价值安全事件配置告警：重复的身份认证失败、提权尝试、来自异常位置的访问以及授权失败
- **日志完整性**：日志必须存储在追加式（append-only）或防篡改的存储中 —— 应用代码不得删除或修改自己的审计日志
- **日志保留**：日志必须至少保留与应用合规要求相适应的期限（默认：至少 90 天）
- **监控仪表盘**：必须为关键运维和安全指标定义监控仪表盘或告警配置

**核验**：
- 为身份认证失败和授权违规配置了告警
- 应用日志组设置了保留策略（至少 90 天）
- 应用角色没有删除自身日志组/日志流的权限
- 安全相关事件（登录失败、访问被拒绝、权限变更）会生成告警

## 规则 SECURITY-15：异常处理与故障安全默认值

**规则**：每个应用都必须安全地处理异常情况：
- **捕获并处理**：所有外部调用（数据库、API、文件 I/O）都必须有显式错误处理 —— 生产环境不允许未处理的 promise 拒绝或未捕获的异常
- **故障关闭（fail closed）**：出错时，系统必须拒绝访问或停止操作 —— 绝不故障开放（fail open）
- **资源清理**：错误路径必须释放资源（连接、文件句柄、锁）—— 使用 try/finally、using 语句或等效模式
- **面向用户的错误**：向用户显示的错误消息必须是通用的 —— 不包含内部详细信息或系统信息
- **全局错误处理器**：应用必须具有全局/顶层错误处理器，捕获未处理的异常、记录它们（按照 SECURITY-03），并返回安全响应

**核验**：
- 所有外部调用（数据库、HTTP、文件 I/O）都有显式错误处理（try/catch、.catch()、错误回调）
- 在应用入口点配置了全局错误处理器
- 错误路径不会绕过授权或验证检查（故障关闭）
- 资源在错误路径中被清理（连接关闭、事务回滚）
- 应用代码中没有未处理的 promise 拒绝或未捕获异常警告

---

## 强制集成

这些规则是适用于每个 AI-DLC 阶段的横切约束。在每个阶段：
- 针对产出的制品评估所有 SECURITY 规则的核验标准
- 在阶段完成摘要中包含 "Security Compliance"（安全合规性）部分，将每条规则列为合规、不合规或 N/A
- 如果任何规则不合规，即为阻断性安全发现 —— 遵循概述中定义的阻断性发现行为
- 在设计文档和测试说明中包含安全规则引用
