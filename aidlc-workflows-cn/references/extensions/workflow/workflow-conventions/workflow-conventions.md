# 工作流约定规则

## 概述

适用于每次 AI-DLC 工作流执行的强制性（MANDATORY）横切规则。本文件没有 `.opt-in.md` —— 它始终强制执行，并在工作流启动时加载。它整合了三组规则：

- **DOC-01~05** 文档一致性 —— 每次变更后保持 aidlc-docs 制品与代码同步
- **APG-01~05** 审批门禁语义 —— 用户在各阶段审批门禁处的回复如何被分类和处理
- **AUD-01~04** 审计署名 —— audit.md 条目的作者字段

**强制执行（Enforcement）**：在每个适用的阶段/门禁，以及每次变更请求之后，在呈现完成消息之前核验是否符合适用规则。包含合规性摘要（每条规则合规 / 不合规 / N/A，并对 N/A 附简要理由）。

### 阻断性发现行为（适用于所有组）

**阻断性发现** 意味着：
1. 在阶段完成消息中列出该发现并附规则编号和描述
2. 在解决之前不提供 "Continue to Next Stage"（只提供带说明的 "Request Changes"；对于 APG/AUD 违规，先修正处理方式/条目）
3. 以规则编号、描述和阶段上下文将该发现记录到 `aidlc-docs/audit.md` 中

所有规则默认都是**阻断性**的。不适用于当前阶段/变更的规则标记为 N/A（不属于发现）。

## 第 1 组：文档一致性（DOC）

### DOC-01：变更到制品的冲击分析
在任何已批准的变更（新增/修改需求、UI 调整、签名/枚举/值域变更）之后，在完成消息之前：
1. 列出受影响的（涉及变更的）关键词、数值范围、类型签名、组件名称、数量
2. 在整个 `aidlc-docs/` 目录树中搜索这些术语的出现（包括已废弃的值）
3. 更新所有包含过期引用的制品，在制品格式支持之处标记变更来源

典型映射：功能 → 需求/故事/业务规则；枚举/范围 → 领域实体、逻辑模型、组件方法；签名 → 组件方法、交互流程；新组件 → 清单、结构树、摘要；测试数量 → 摘要覆盖部分。

**核验**：对 `aidlc-docs/` 的 grep 显示，已维护的制品中没有过期的变更前值；新概念出现在每个枚举该类别的制品中；交叉引用/覆盖表包含已变更的条目。

### DOC-02：同一交互内的计划跟踪
每个变更请求 —— 包括小修复和视觉调整 —— 必须作为一步追加到相关阶段计划文件中，并在工作完成的**同一交互**中标记为 `[x]`。

**核验**：计划文件包含该步骤并带有故事/需求可追溯性，且在同一个交互中勾选；不存在没有已勾选计划步骤的已完成代码变更。

### DOC-03：完成核验中的文档门禁
完成核验除代码级核验（编译/静态检查/测试/构建）外，必须包含 DOC-01 全量扫描。代码通过不代表完成通过。摘要中陈述的结果必须反映最近一次运行（当前测试数量，而非复制的值）。

### DOC-04：历史记录仅可追加
问答文件、计划文件的澄清部分以及 `audit.md` 条目不得被追溯重写。更正和新的决策作为新的带时间戳条目追加。

**核验**：没有任何历史问答回答或 audit 条目被原地编辑；被取代的决策后面跟有更新的带时间戳条目。

### DOC-05：通用制品，无跨项目泄漏
共享工作流规则文件不得包含任何项目特定的标识符（项目名称、来自某个项目的需求/故事编号）。项目特定内容属于该项目的 `aidlc-docs/`，绝不属于共享规则。

## 第 2 组：审批门禁语义（APG）

阶段完成消息保持其标准化的双选项模板不变 —— 本组是对用户自由文本回复的解释层。

### APG-01：审批意图分类
在每个审批门禁处，在采取行动之前，将用户的回复准确分类为一种意图：

| 意图 | 触发语义 | 示例（非穷尽） |
|---|---|---|
| 批准并暂停（Approve-and-Hold） | 仅批准，无继续信号 | "approve", "approved", "ok", "okay", "yes", "lgtm", "同意", "批准", "好的", "可以", "没问题" |
| 批准并继续（Approve-and-Continue） | 继续（隐含批准） | "continue", "go on", "next", "proceed", "继续", "继续吧", "下一步", "接着来", "往下走" |
| 请求变更（Request Changes） | 任何修改/提问/更正 | 按各阶段规则的现有行为 |

- 批准 + 无关的额外指令（例如 "批准但不要进入下一步，只提交代码"）→ **批准并暂停**；只执行该明确指令，然后询问是否继续。
- 在暂停/继续之间确实含糊不清 → **批准并暂停**（含糊时绝不自动开始下一阶段工作）。

**核验**：每个审批回复都以分类后的意图记录在 audit.md 中；暂停时不开始任何下一阶段工作；含糊默认视为暂停。

### APG-02：批准并暂停行为
在批准并暂停时，在**同一交互**中：
1. 在 `aidlc-docs/aidlc-state.md` 中将阶段标记为已批准并等待继续（例如 "approved (hold) - awaiting continue to [Next Stage]"）
2. 在 audit.md 中记录批准，附完整原始输入和意图 "approve-hold"
3. 不开始任何下一阶段工作（无制品、无计划、无执行）
4. 以明确的继续问题结束回复，指明确切的下一阶段

### APG-03：批准并继续行为
在批准并继续时：与标准 "Approve & Continue" 选项完全一致 —— 标记完成，以意图 "approve-continue" 记录，并在同一交互中立即继续。

### APG-04：从暂停状态恢复
- 在已暂停的门禁处收到继续信号，无需重新批准即可进入记录的下一阶段；更新状态并记录恢复。
- 在已暂停的门禁处收到新指令（例如变更请求）时，在收到明确的继续信号之前，门禁保持暂停。

**核验**：恢复时从不重新请求批准；下一阶段开始后，状态文件从不显示已暂停的门禁；中途的请求不会丢失暂停状态。

### APG-05：不修改模板
完成消息模板和 "NO EMERGENT BEHAVIOR" 约束与阶段规则文件中的定义完全一致。绝不添加第三个可见选项；暂停/继续通过用户的自然语言回复来表达。

## 第 3 组：审计署名（AUD）

### AUD-01：每条新条目的作者字段
追加到 `aidlc-docs/audit.md` 的每条**新**条目，必须在 `**Context**` 行之后立即包含以下两行：

```markdown
**User**: [resolved git user.name]
**Email**: [resolved git user.email]
```

适用于所有条目类型，包括自动化的 `[No user input]` 条目。

### AUD-02：从 Git 配置解析值
写入时动态解析，绝不硬编码：
1. 在工作区仓库中运行 `git config user.name` 和 `git config user.email`（本地配置自动优先）
2. 无法解析（无 git / 非仓库 / 键未设置）→ 写入 `unknown`，绝不阻塞工作流
3. 每次 audit 写入时重新解析（不做跨会话缓存）

### AUD-03：历史条目不动
仅适用于采用后创建的条目；现有条目不得被追溯编辑（与 DOC-04 一致）。

### AUD-04：通用规则文本
本规则文件不得包含任何真实人员的姓名或邮箱 —— 仅含占位符和解析说明。

| 本文件自身的维护 | DOC-05, AUD-04 |
