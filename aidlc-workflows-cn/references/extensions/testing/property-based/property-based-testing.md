# 基于属性的测试规则

## 概述

这些基于属性的测试（PBT）规则是适用于相关 AI-DLC 阶段的横切约束。它们确保具有可识别属性的代码使用基于属性的技术进行测试，以补充（而非取代）传统的基于示例的测试。

基于属性的测试定义了对所有有效输入都必须成立的不变量，然后使用框架生成随机输入并搜索反例。当发现失败时，框架会将输入收缩为最小的可重现案例。这种方法能够发现基于示例的测试通常会遗漏的边界情况和微妙缺陷。

**强制执行（Enforcement）**：在每个适用阶段，模型在向用户呈现阶段完成消息之前，必须核验是否符合这些规则。

### 阻断性 PBT 发现行为

**阻断性 PBT 发现（blocking PBT finding）** 意味着：
1. 该发现必须在阶段完成消息的 "PBT Findings" 部分下列出，并附上 PBT 规则编号和描述
2. 在所有阻断性发现解决之前，阶段不得提供 "Continue to Next Stage"（继续到下一阶段）选项
3. 模型只能提供 "Request Changes"（请求变更）选项，并清楚说明需要变更的内容
4. 该发现必须记录到 `aidlc-docs/audit.md` 中，并附上 PBT 规则编号、描述和阶段上下文

如果某条 PBT 规则不适用于当前项目或单元（例如不存在有状态组件时的 PBT-06），请在合规性摘要中将其标记为 **N/A** —— 这不属于阻断性发现。

### 默认强制执行

本文档中的所有规则默认都是**阻断性**的。如果任何规则的核验标准未满足，即为阻断性 PBT 发现 —— 请遵循上述阻断性发现行为。

### 部分强制执行模式

如果用户在选择加入时选择了**部分（Partial）**强制执行，则只强制执行 PBT-02、PBT-03、PBT-07、PBT-08 和 PBT-09 这些规则。所有其他规则视为建议性（非阻断性）规则。将强制执行模式记录在 `aidlc-docs/aidlc-state.md` 的 `## Extension Configuration` 下。

### 核验标准格式

本文档中的核验项是描述合规性检查的普通要点。审查期间，每个条目都应评估为合规或不合规。

## 规则 PBT-01：设计期间的属性识别

**规则**：包含业务逻辑、数据转换或算法操作的每个单元，都必须在功能设计（Functional Design）阶段分析可测试的属性。分析必须识别以下属性类别中哪些适用：

| 类别 | 描述 | 示例 |
|---|---|---|
| Round-trip | 与逆操作配对时还原原始值 | serialize → deserialize = identity |
| Invariant | 变换保持某种可度量的特征 | sort preserves collection size and elements |
| Idempotence | 对操作应用两次与应用一次结果相同 | dedup(dedup(list)) = dedup(list) |
| Commutativity | 不同的操作顺序产生相同的结果 | add(a, b) = add(b, a) |
| Oracle | 参考实现或简化模型可以验证结果 | optimized algorithm vs brute-force |
| Induction | 对小输入成立的属性可推广到更大的输入 | recursive structures, divide-and-conquer |
| Easy verification | 结果难以计算但易于检查 | maze solver output can be walked to verify |

识别出的属性必须记录在该单元的功能设计制品中，并作为 PBT 测试需求带入代码生成阶段。

**核验**：
- 功能设计制品包含 "Testable Properties"（可测试属性）部分，按组件列出识别出的属性
- 每个识别出的属性都引用上述类别之一
- 没有可识别属性的组件被明确标记为 "No PBT properties identified"（未识别出 PBT 属性）并附简要理由
- 属性列表在代码生成规划期间被引用

---

## 规则 PBT-02：往返（Round-Trip）属性

**规则**：任何具有逻辑逆操作的操作都必须有一个基于属性的测试来验证往返。这包括但不限于：
- 序列化 / 反序列化（JSON、XML、Protobuf、二进制格式）
- 编码 / 解码（Base64、URL 编码、压缩）
- 解析 / 格式化（日期解析、数字格式化、带结构化输入的模板渲染）
- 加密 / 解密（密钥可用时）
- 数据库写入 / 读取（针对数据转换层，而非 I/O 本身）
- 任何满足对于所有有效 `x` 有 `f_inverse(f(x)) = x` 的函数对

基于属性的测试必须使用领域合适的生成器（参见 PBT-07）生成随机有效输入，并断言往返产生的值等于原始输入。

**核验**：
- 每个序列化/反序列化对都有往返属性测试
- 每个编码/解码对都有往返属性测试
- 每个解析/格式化对都有往返属性测试（或记录该转换为何是有损的）
- 往返测试使用生成的输入，而非硬编码的示例
- 有损转换（例如存在精度损失的浮点格式化）记录可接受的偏差并在容差范围内测试

---

## 规则 PBT-03：不变量（Invariant）属性

**规则**：具有已记录不变量的函数必须有基于属性的测试来验证这些不变量在生成的输入上成立。常见的不变量包括：
- **大小保持**：输出集合与输入大小相同（例如 map、sort）
- **元素保持**：输出恰好包含与输入相同的元素，可能重新排序（例如 sort、shuffle）
- **顺序保证**：输出满足排序约束（例如 sort 产生非递减顺序）
- **范围约束**：输出值落在定义的范围内（例如 normalize 产生 [0, 1] 范围内的值）
- **类型保持**：对所有有效输入，输出类型与预期类型匹配
- **业务规则不变量**：必须始终成立的领域特定规则（例如"有效交易后账户余额永不为负"、"折扣永不超过商品价格"）

**核验**：
- 每个已记录的不变量都有对应的基于属性的测试
- 不变量测试生成广泛范围的输入，包括边界值
- 功能设计中识别出的业务规则不变量由 PBT 覆盖
- 不变量测试不重复基于示例的测试中的精确断言 —— 它们测试的是通用规则，而非特定案例

---

## 规则 PBT-04：幂等性属性

**规则**：任何声称或要求幂等性的操作都必须有基于属性的测试来证明它。测试必须验证对所有有效生成的输入都有 `f(f(x)) = f(x)`。这适用于：
- 被记录为幂等的 API 端点（PUT、DELETE）
- 数据规范化或净化函数
- 缓存填充操作
- 去重逻辑
- 配置应用（应用配置两次不应改变状态）
- 至少一次投递系统中的消息处理

**核验**：
- 每个被记录为幂等的操作都有断言 `f(f(x)) = f(x)` 的 PBT
- 幂等性测试使用领域合适的生成器（不仅仅是原始类型）
- 对于有状态操作，测试验证单次应用与重复应用后的可观察状态等价性

---

## 规则 PBT-05：Oracle 与基于模型的测试

**规则**：当存在参考实现、简化模型或已知正确的算法时，基于属性的测试必须将被测系统与 oracle 进行比较。这适用于：
- 取代已知暴力版本优化算法
- 取代遗留实现的重构代码
- 与顺序版本进行比较的并行/并发实现
- 知名算法的自定义实现（排序、搜索、图遍历）
- 与参考数据库进行比较的新查询引擎

基于属性的测试必须生成随机有效输入，并断言被测系统对所有生成的输入都产生与 oracle 等价的结果。

**核验**：
- 当参考实现存在（或可以轻松编写）时，存在 oracle PBT
- Oracle 测试生成涵盖正常、边界和对抗性案例的多样化输入
- 等价性被精确定义（精确相等、结构相等或记录的容差）
- 如果不存在 oracle，此规则标记为 N/A 并附理由

---

## 规则 PBT-06：有状态属性测试

**规则**：管理可变状态的组件必须评估是否适合有状态属性测试。有状态 PBT 针对系统生成随机命令（操作）序列，并验证每步之后不变量仍然成立。这适用于：
- 内存缓存和数据存储
- 状态机和工作流引擎
- 队列和缓冲区实现
- 会话管理系统
- 购物车、订单流水线及类似的有状态业务对象
- 任何操作结果取决于先前操作的组件

有状态 PBT 必须：
- 定义镜像被测系统的简化模型（参考状态）
- 生成随机的有效命令序列（add、remove、update、query 等）
- 对真实系统和模型都执行每条命令
- 断言每条命令之后系统与模型之间的可观察状态或查询结果一致
- 测试不同长度的序列，包括空序列

**核验**：
- 功能设计中识别出的有状态组件具有有状态 PBT，或记录其为何不适用
- 定义了用于比较的简化模型
- 命令生成器生成带有真实参数分布的有效操作序列
- 在序列中的每条命令之后检查不变量，而不仅仅在结尾
- 如果不存在有状态组件，此规则标记为 N/A

---

## 规则 PBT-07：生成器质量

**规则**：基于属性的测试必须使用领域特定的生成器，产生真实、结构化的输入 —— 而不仅仅是原始类型。糟糕的生成器（例如为电子邮件字段生成随机字符串、为年龄字段生成无界整数）会产生无意义的测试用例并错过真正的缺陷。

生成器要求：
- **领域类型**：必须为领域对象（例如 User、Order、Transaction）创建尊重业务约束（有效电子邮件格式、正数金额、有效日期范围）的自定义生成器
- **受约束的原始类型**：在领域要求时，数字生成器必须约束到真实的范围内
- **结构化数据**：复杂输入（嵌套对象、领域对象列表）的生成器必须产生结构上有效的数据
- **包含边界案例**：生成器应该（SHOULD）配置为在正常值之外包含边界值（空集合、零、最大值、Unicode 字符串）
- **可复用性**：领域生成器应该（SHOULD）定义为可复用的测试工具，而不是在测试文件间重复

**核验**：
- 没有 PBT 只对领域类型参数使用原始生成器（例如单独使用 `st.integers()`）
- 为 PBT 中使用的领域对象存在自定义生成器
- 生成器尊重已记录的业务约束（例如正数金额、有效格式）
- 当多个测试共享相同的领域类型时，生成器定义集中化且可复用

---

## 规则 PBT-08：收缩与可复现性

**规则**：所有基于属性的测试都必须支持收缩和确定性可复现。

- **收缩（Shrinking）**：当属性失败时，PBT 框架必须自动将失败的输入缩减为最小的可重现案例。除非有记录的技术原因（例如收缩与集成测试中的外部服务调用不兼容），否则测试不得禁用或绕过框架的收缩机制。
- **可复现性**：每次 PBT 运行都必须能通过种子值复现。失败时必须记录种子，以便可以重放精确的失败场景。CI 配置必须使用固定种子进行确定性运行，或在每次运行时记录随机种子以便失败后复现。
- **CI 集成**：PBT 必须包含在项目的 CI 流水线中。不稳定（flaky）的 PBT 失败（未改动代码重试即通过的测试）必须调查，而不是被抑制。

**核验**：
- 启用了 PBT 框架的收缩（未被覆盖或禁用）
- 失败时的测试输出包含种子值和收缩后的最小失败输入
- CI 配置记录每次 PBT 运行的种子，或使用固定种子
- 没有 PBT 在没有记录理由的情况下被排除在 CI 之外
- 不稳定的 PBT 失败被跟踪和调查，而不是被静默重试

---

## 规则 PBT-09：框架选择

**规则**：项目必须为其主要语言选择并配置合适的基于属性的测试框架。该框架必须支持：
- 领域类型的自定义生成器/策略
- 失败案例的自动收缩
- 基于种子的可复现性
- 与项目现有测试运行器的集成

按语言推荐框架（非穷尽列表）：

| 语言 | 框架 | 说明 |
|---|---|---|
| Python | Hypothesis | 成熟、出色的收缩、Django 集成 |
| JavaScript / TypeScript | fast-check | 与 Jest、Vitest、Mocha 集成 |
| Java | jqwik | JUnit 5 集成、支持有状态测试 |
| Kotlin | Kotest Property Testing | Kotest 框架集成 |
| Scala | ScalaCheck | SBT 集成、被广泛采用 |
| Rust | proptest | 基于宏、收缩良好 |
| Go | rapid | 轻量、地道的 Go |
| Haskell | QuickCheck | 最初的 PBT 框架 |
| C# / .NET | FsCheck | 适用于 xUnit、NUnit |
| Erlang / Elixir | PropEr / StreamData | 感知 OTP、支持有状态测试 |

所选框架必须记录在技术栈决策中，并作为项目依赖包含在内。

**核验**：
- 选择了一个 PBT 框架并记录在技术栈决策中
- 该框架包含在项目依赖中（package.json、pom.xml、requirements.txt 等）
- 该框架支持自定义生成器、收缩和基于种子的可复现性
- 如果项目使用多种语言，每种包含 PBT 适用代码的语言都选择了框架

---

## 规则 PBT-10：互补测试策略

**规则**：基于属性的测试必须补充而非取代基于示例的测试。这两种方法服务于不同的目的：

- **基于示例的测试**：以显式的预期值记录特定的已知场景、回归案例和业务关键边界案例。它们是具体行为的可执行文档。
- **基于属性的测试**：在广泛的输入空间上验证通用不变量。它们发现未知的边界案例并验证属性在普遍范围内成立。

要求：
- 用户故事或需求中识别出的关键业务场景必须有显式的基于示例的测试，即使 PBT 覆盖了相同的属性
- PBT 不得是任何业务关键路径的唯一测试 —— 至少有一个基于示例的测试必须固定关键场景的预期行为
- 当 PBT 发现失败案例时，收缩后的最小示例应该（SHOULD）作为永久性的基于示例的回归测试添加
- 测试文档必须清楚地区分基于示例的测试和基于属性的测试（单独的测试文件、测试类或命名清晰的测试函数）

**核验**：
- 业务关键路径同时具有基于示例的和基于属性的测试
- 任何关键功能都没有只依赖 PBT 作为唯一测试覆盖
- 测试文件或测试类清楚地区分或标注 PBT 与基于示例的测试
- PBT 发现的失败所产生的回归测试被捕获为永久性的基于示例的测试

## 强制集成

这些规则是适用于以下 AI-DLC 阶段的横切约束：

| 阶段 | 适用规则 | 强制机制 |
|---|---|---|
| 功能设计（Functional Design） | PBT-01 | 属性识别必须出现在设计制品中 |
| NFR 需求（NFR Requirements） | PBT-09 | 框架选择必须包含在技术栈决策中 |
| 代码生成（规划） | PBT-01 至 PBT-10 | 代码生成计划必须包含针对已识别属性的 PBT 测试步骤 |
| 代码生成（生成） | PBT-02 至 PBT-08、PBT-10 | 生成的测试必须包含与基于示例的测试并行的 PBT |
| 构建与测试（Build and Test） | PBT-08 | 测试执行说明必须包含带种子日志和 CI 集成的 PBT |

在每个适用阶段：
- 针对产出的制品评估所有 PBT 规则的核验标准
- 在阶段完成摘要中包含 "PBT Compliance"（PBT 合规性）部分，将每条规则列为合规、不合规或 N/A
- 如果任何规则不合规，即为阻断性 PBT 发现 —— 遵循概述中定义的阻断性发现行为
- 在设计文档和测试说明中包含 PBT 规则引用

## 附录：属性类别快速参考

供在功能设计（PBT-01）期间识别属性的开发者和 AI 模型参考：

| 模式名称 | 正式术语 | 测试形态 | 使用时机 |
|---|---|---|---|
| There and back again | Invertible function | `f_inv(f(x)) == x` | 序列化、编码、解析 |
| Some things never change | Invariant | `measure(f(x)) == measure(x)` | 排序、映射、过滤、变换 |
| The more things change, the more they stay the same | Idempotence | `f(f(x)) == f(x)` | 规范化、去重、缓存写入 |
| Different paths, same destination | Commutativity | `f(g(x)) == g(f(x))` | 算术、集合运算、独立变换 |
| Solve a smaller problem first | Structural induction | Property on `x` implies property on `x + element` | 递归结构、列表、树 |
| Hard to prove, easy to verify | Verification | `verify(solve(x)) == true` | 求解器、优化器、搜索算法 |
| The test oracle | Reference comparison | `f(x) == oracle(x)` | 优化版 vs 暴力版、重构版 vs 遗留版 |

来源：属性类别分类法改编自 Scott Wlaschin 的 "Choosing properties for property-based testing"（[fsharpforfunandprofit.com](https://fsharpforfunandprofit.com/posts/property-based-testing-2/)）。
