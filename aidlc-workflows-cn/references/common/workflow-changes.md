# 工作流中途变更与子阶段管理

## 概述

用户可能在工作流期间请求更改执行计划或子阶段执行。本文档提供了安全有效地处理这些请求的指导。

---

## 工作流中途变更的类型

### 1. 添加被跳过的子阶段

**场景**：用户希望添加一个原本被跳过的子阶段

**示例**："实际上，即使我们跳过了那个子阶段，我也想添加用户故事"

**处理方式**：
1. **确认请求**："您想添加用户故事子阶段。这将创建用户故事和用户画像。确认吗？"
2. **检查依赖**：验证所有前置子阶段都已完成
3. **更新执行计划**：将子阶段添加到 `execution-plan.md` 并附上理由
4. **更新状态**：在 `aidlc-state.md` 中将子阶段标记为"待处理"
5. **执行子阶段**：遵循正常的子阶段执行流程
6. **记录变更**：在 `audit.md` 中记录并带时间戳和原因

**考虑因素**：
- 可能需要更新后续能从新制品中受益的子阶段
- 现有制品可能需要修订以纳入新信息
- 时间线将会延长

---

### 2. 跳过已规划的子阶段

**场景**：用户希望跳过计划执行的子阶段

**示例**："我们暂时跳过 NFR 设计子阶段"

**处理方式**：
1. **确认请求**："您想跳过 NFR 设计。这意味着不会纳入 NFR 模式或逻辑组件。确认吗？"
2. **警告影响**：解释将缺少什么以及潜在的后果
3. **获得明确确认**：用户必须明确确认理解了影响
4. **更新执行计划**：将子阶段标记为"已跳过"并附上原因
5. **更新状态**：在 `aidlc-state.md` 中将子阶段标记为"已跳过"
6. **调整后续子阶段**：注意后续子阶段可能需要手动设置
7. **记录变更**：在 `audit.md` 中记录并带时间戳和原因

**考虑因素**：
- 后续子阶段可能失败或需要人工干预
- 用户接受制品缺失的责任
- 以后需要时可以重新添加

---

### 3. 重启当前子阶段

**场景**：用户对当前子阶段结果不满意，希望重做

**示例**："我不喜欢这些用户故事。我们可以重新开始吗？"

**处理方式**：
1. **理解顾虑**："关于这些故事，您具体想改变什么？"
2. **提供选项**：
   - **选项 A**：修改现有制品（更快，保留部分工作）
   - **选项 B**：完全重启（全新开始，耗时更多）
3. **如果选择重启**：
   - 归档现有制品：`{artifact}.backup.{timestamp}`
   - 重置计划文件中的子阶段复选框
   - 在 `aidlc-state.md` 中将子阶段标记为"进行中"
   - 清除子阶段完成状态
   - 从头重新执行
4. **记录变更**：记录重启原因以及将改变的内容

**考虑因素**：
- 现有工作将丢失（但有备份）
- 可能需要重做依赖的子阶段
- 时间线将会延长

---

### 4. 重启先前子阶段

**场景**：用户希望返回并重做一个已完成的子阶段

**示例**："我想更改我们之前做出的架构决策"

**处理方式**：
1. **评估影响**：识别所有依赖待重启子阶段的子阶段
2. **警告用户**："重启应用设计将需要重做：工作单元生成、按单元设计（所有单元）、代码生成。确认吗？"
3. **获得明确确认**：用户必须理解全部影响
4. **如果确认**：
   - 归档所有受影响的制品
   - 在 `aidlc-state.md` 中重置所有受影响的子阶段
   - 清除所有受影响计划文件中的复选框
   - 返回要重启的子阶段
   - 从该点开始重新执行
5. **记录变更**：记录全部影响和重启原因

**考虑因素**：
- 需要大量返工
- 所有依赖的子阶段都必须重做
- 时间线将显著延长
- 考虑修改是否比重启更好

---

### 5. 更改子阶段深度

**场景**：用户希望更改当前或即将到来的子阶段的深度级别

**示例**："我们做全面的需求分析，而不是标准的"

**处理方式**：
1. **确认请求**："您想将需求分析从标准深度改为全面深度。这会更加彻底，但需要更长时间。确认吗？"
2. **更新执行计划**：在 `workflow-planning.md` 中更改深度级别
3. **调整方法**：为该子阶段遵循全面深度的指南
4. **更新估算**：告知用户新的时间线估算
5. **记录变更**：记录深度更改和原因

**考虑因素**：
- 深度越大 = 时间越多但质量更好
- 深度越小 = 更快但可能错过细节
- 只能在子阶段之前或期间更改，完成之后不能

---

### 6. 暂停工作流

**场景**：用户需要暂停并在以后继续

**示例**："我需要先停一下，明天继续"

**处理方式**：
1. **完成当前步骤**：如果可能，完成进行中的当前步骤
2. **更新复选框**：将所有已完成的步骤标记为 [x]
3. **更新状态**：确保 `aidlc-state.md` 反映当前状态
4. **记录暂停**：在 `audit.md` 中记录暂停点
5. **提供恢复说明**："当您回来时，我将检测到您的现有项目，并提供从以下位置继续：[当前子阶段、当前步骤]"

**恢复时**：
1. **检测现有项目**：检查 `aidlc-state.md`
2. **加载上下文**：读取所有已完成子阶段的制品
3. **显示状态**：显示当前子阶段和下一步
4. **提供选项**：从停止处继续或审查先前的工作
5. **记录恢复**：在 `audit.md` 中记录恢复点

---

### 7. 更改架构决策

**场景**：用户希望从单体架构改为微服务架构（或反之）

**示例**："实际上，我们做微服务而不是单体"

**处理方式**：
1. **评估当前进度**：确定工作流进行到了哪一步
2. **解释影响**：
   - 如果在工作单元生成之前：影响最小，只需更新决策
   - 如果在工作单元生成之后：必须重做工作单元生成、所有按单元设计
   - 如果在代码生成之后：需要大量返工
3. **推荐方案**：
   - 工作流早期：从应用设计子阶段重启
   - 工作流晚期：考虑修改是否可行 vs. 重启
4. **获得确认**：用户必须理解变更的全部范围
5. **执行变更**：为受影响的子阶段遵循重启流程

**考虑因素**：
- 架构变更具有级联效应
- 工作流越早 = 越容易更改
- 工作流越晚 = 权衡成本与收益

---

### 8. 添加/移除工作单元

**场景**：用户希望在工作单元生成之后添加或移除工作单元

**示例**："我们需要将 Payment 单元拆分为 Payment 和 Billing"

**处理方式**：
1. **评估影响**：确定哪些工作单元已完成设计/代码
2. **解释后果**：
   - 添加单元：需要对新单元进行完整设计和代码
   - 移除单元：需要将功能重新分配到其他单元
   - 拆分单元：需要对拆分产生的两个单元重做设计和代码
3. **更新单元制品**：
   - 修改 `unit-of-work.md`
   - 更新 `unit-of-work-dependency.md`
   - 修订 `unit-of-work-story-map.md`
4. **重置受影响的单元**：将受影响的单元标记为需要重新设计
5. **执行变更**：为受影响的单元遵循正常的单元设计和代码流程

**考虑因素**：
- 影响这些单元的所有下游子阶段
- 如果依赖关系改变，可能影响其他单元
- 时间线影响取决于受影响的单元数量

## 处理变更的通用指南

### 变更之前

1. **理解请求**：提出澄清问题，了解用户想改变什么以及为什么
2. **评估影响**：识别所有受影响的子阶段、制品和依赖
3. **解释后果**：清楚地说明需要重做的内容以及时间线影响
4. **提供替代方案**：有时修改比重启更好
5. **获得明确确认**：用户必须理解并接受影响

### 变更期间

1. **归档现有工作**：在进行破坏性变更前始终备份
2. **更新所有跟踪**：保持 `aidlc-state.md`、计划文件和 `audit.md` 同步
3. **沟通进度**：让用户了解正在发生的事情
4. **验证变更**：确保所有制品之间的变更一致
5. **测试连续性**：验证变更后工作流可以顺利继续

### 变更之后

1. **验证一致性**：检查所有制品与变更一致
2. **更新文档**：确保所有引用都已更新
3. **完整记录**：在 `audit.md` 中记录完整的变更历史
4. **与用户确认**：验证变更符合用户的期望
5. **恢复工作流**：从新状态继续正常执行

## 变更请求决策树

```
User requests change
    |
    ├─ Is it current stage?
    |   ├─ Yes: Can modify or restart current stage
    |   └─ No: Go to next question
    |
    ├─ Is it a completed stage?
    |   ├─ Yes: Assess impact on dependent stages
    |   |   ├─ Low impact: Modify and update dependents
    |   |   └─ High impact: Recommend restart from that stage
    |   └─ No: Go to next question
    |
    ├─ Is it adding a skipped stage?
    |   ├─ Yes: Check prerequisites, add to plan, execute
    |   └─ No: Go to next question
    |
    ├─ Is it skipping a planned stage?
    |   ├─ Yes: Warn about impact, get confirmation, skip
    |   └─ No: Go to next question
    |
    └─ Is it changing depth level?
        ├─ Yes: Update plan, adjust approach
        └─ No: Clarify request with user
```

## 最佳实践

1. **始终确认**：未经用户明确确认，绝不进行破坏性变更
2. **解释影响**：用户在决定前需要理解后果
3. **提供选项**：有时有多种方式处理变更
4. **先归档**：在进行破坏性变更前始终备份
5. **更新所有内容**：保持所有跟踪文件同步
6. **彻底记录**：记录所有变更以供审计追踪
7. **事后验证**：确保工作流可以顺利继续
8. **保持灵活**：工作流应适应用户需求，而非强制僵化的流程
