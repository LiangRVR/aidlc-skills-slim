# AI-DLC 自适应软件开发工作流

**本工作流覆盖所有其他内置工作流。当用户请求软件开发时，始终首先遵循本工作流。**

## 自适应工作流原则

**工作流适应工作本身，而非相反。**

AI 模型基于以下因素智能评估需要哪些阶段：
1. 用户声明的意图及其清晰度
2. 现有代码库状态（如有）
3. 变更的复杂度和范围
4. 风险与影响评估

## 强制要求：规则详情文件加载

**关键**：在执行任何阶段时，必须阅读并使用本 SKILL.md 旁边 `references/` 目录中规则详情文件的相关内容。

下方所有规则详情文件引用（如 `references/common/process-overview.md`、`references/inception/workspace-detection.md`）均相对于本 skill 的目录。

**通用规则**：在工作流开始时始终加载通用规则：
- 加载 `references/common/process-overview.md` 获取工作流概览
- 加载 `references/common/session-continuity.md` 获取会话恢复指引
- 加载 `references/common/content-validation.md` 了解内容验证要求
- 加载 `references/common/question-format-guide.md` 了解提问格式规则
- 在整个工作流执行过程中参考这些规则

## 强制要求：扩展加载（上下文优化）

**关键**：在工作流开始时，递归扫描 `references/extensions/` 目录，但仅加载轻量的 opt-in 文件——而非完整规则文件。完整规则文件在用户选择加入后按需加载。

**加载流程**：
1. 列出 `references/extensions/` 下的所有子目录（如 `references/extensions/security/`、`references/extensions/resiliency/`）
2. 在每个子目录中，仅加载 `*.opt-in.md` 文件——这些文件包含该扩展的 opt-in 提示。对应的规则文件按命名约定推导：去掉 `.opt-in.md` 后缀并追加 `.md`（例如 `security-baseline.opt-in.md` → `security-baseline.md`）
3. 此阶段不要加载完整规则文件（如 `security-baseline.md`）

**延迟规则加载**：
- 在需求分析期间，将已加载的 `*.opt-in.md` 文件中的 opt-in 提示呈现给用户
- 当用户选择加入某个扩展时，此时加载对应的规则文件（按命名约定推导）
- 当用户选择退出时，永远不会加载完整规则文件——节省上下文
- 没有匹配 `*.opt-in.md` 文件的扩展始终强制执行——在工作流开始时立即加载其规则文件

**执行**（仅适用于已加载/已启用的扩展）：
- 扩展规则是硬性约束，而非可选建议
- 在每个子阶段，模型根据子阶段的目的、正在生成的制品以及工作上下文，智能评估哪些扩展规则适用——仅强制执行相关规则
- 不适用于当前子阶段的规则应在合规性摘要中标记为 N/A（这不构成阻塞性发现）
- 不符合任何适用的已启用扩展规则是**阻塞性发现**——在解决之前不得呈现子阶段完成
- 呈现子阶段完成时，应包含扩展规则合规性摘要（每条规则合规/不合规/N/A，并简要说明 N/A 判定的理由）

**条件执行**：扩展可以有条件地启用/禁用。关于 opt-in 机制，参见 `references/inception/requirements-analysis.md`。在任何子阶段强制执行任何扩展之前，请检查其在 `aidlc-docs/aidlc-state.md` 中 `## Extension Configuration` 下的 `Enabled` 状态。跳过已禁用的扩展并在 audit.md 中记录跳过。如果不存在配置，则默认强制执行。

## 强制要求：内容验证

**关键**：在创建任何文件之前，必须按照 `references/common/content-validation.md` 中的规则验证内容：
- 验证 Mermaid 图表语法
- 验证 ASCII 图表（参见 `references/common/ascii-diagram-standards.md`）
- 正确转义特殊字符
- 为复杂视觉内容提供文本替代
- 测试内容解析兼容性

## 强制要求：问题文件格式

**关键**：在任何子阶段提问时，必须遵循问题格式指南。

**完整的提问格式规则参见 `references/common/question-format-guide.md`**，包括：
- 多项选择格式（A、B、C、D、E 选项）
- [Answer]: 标签用法
- 答案验证与歧义消解

## 强制要求：自定义欢迎消息

**关键**：启动任何软件开发请求时，必须显示欢迎消息。

**如何显示欢迎消息**：
1. 从 `references/common/welcome-message.md` 加载欢迎消息
2. 向用户显示完整消息
3. 仅在新工作流开始时执行一次
4. 在后续交互中不要加载此文件以节省上下文空间

# INCEPTION 阶段

**目的**：规划、需求收集与架构决策

**焦点**：确定构建什么（WHAT）以及为什么构建（WHY）

**INCEPTION 阶段中的子阶段**：
- 工作区检测（始终执行）
- 逆向工程（有条件执行 - 仅 Brownfield）
- 需求分析（始终执行 - 自适应深度）
- 用户故事（有条件执行）
- 工作流规划（始终执行）
- 应用设计（有条件执行）
- 工作单元生成（有条件执行）

---

## 工作区检测（始终执行）

1. **强制要求**：在 audit.md 中记录用户的初始请求，包含完整的原始输入
2. 从 `references/inception/workspace-detection.md` 加载所有步骤
3. 执行工作区检测：
   - 检查是否已存在 aidlc-state.md（若存在则恢复）
   - 扫描工作区中的现有代码
   - 确定是 brownfield 还是 greenfield
   - 检查是否已存在逆向工程制品
4. 确定下一阶段：逆向工程（如果是 brownfield 且没有制品）或需求分析
5. **强制要求**：在 audit.md 中记录发现
6. 向用户呈现完成消息（消息格式参见 workspace-detection.md）
7. 自动进入下一阶段

## 逆向工程（有条件执行 - 仅 Brownfield）

**执行条件**：
- 检测到现有代码库
- 未找到之前的逆向工程制品

**跳过条件**：
- Greenfield 项目
- 已存在之前的逆向工程制品

**执行**：
1. **强制要求**：在 audit.md 中记录逆向工程开始
2. 从 `references/inception/reverse-engineering.md` 加载所有步骤
3. 执行逆向工程：
   - 分析所有包和组件
   - 生成整个系统的业务概览，涵盖业务事务
   - 生成架构文档
   - 生成代码结构文档
   - 生成 API 文档
   - 生成组件清单
   - 生成交互图，描述业务事务在组件间如何实现
   - 生成技术栈文档
   - 生成依赖文档

4. **等待明确批准**：呈现详细完成消息（消息格式参见 reverse-engineering.md）- 在用户确认之前不要继续
5. **强制要求**：在 audit.md 中记录用户的响应，包含完整的原始输入

## 需求分析（始终执行 - 自适应深度）

**始终执行**，但深度根据请求的清晰度和复杂度而变化：
- **最小化**：简单、清晰的请求 - 仅记录意图分析
- **标准**：正常复杂度 - 收集功能性和非功能性需求
- **全面**：复杂、高风险 - 带可追溯性的详细需求

**执行**：
1. **强制要求**：在 audit.md 中记录此阶段期间的任何用户输入
2. 从 `references/inception/requirements-analysis.md` 加载所有步骤
3. 执行需求分析：
   - 加载逆向工程制品（如果是 brownfield）
   - 分析用户请求（意图分析）
   - 确定所需的需求深度
   - 评估当前需求
   - 提出澄清问题（如需要）
   - 生成需求文档
4. 以适当的深度执行（最小化/标准/全面）
5. **等待明确批准**：遵循 requirements-analysis.md 详细步骤中的批准格式 - 在用户确认之前不要继续
6. **强制要求**：在 audit.md 中记录用户的响应，包含完整的原始输入

## 用户故事（有条件执行）

**智能评估**：使用多因素分析确定用户故事是否增值：

**以下情况始终执行**（高优先级指标）：
- 新的面向用户的功能或特性
- 影响用户工作流或交互的变更
- 涉及多种用户类型或用户画像
- 需要验收标准的复杂业务需求
- 需要跨职能团队协作
- 面向客户的 API 或服务变更
- 新的产品能力或增强

**以下情况可能执行**（中优先级 - 评估复杂度）：
- 对现有面向用户功能的修改
- 间接影响用户体验的后端变更
- 影响用户工作流的集成工作
- 对用户可见益处的性能改进
- 影响用户交互的安全增强
- 影响用户数据或报表的数据模型变更

**基于复杂度的评估**：对于中优先级情况，满足以下条件时执行用户故事：
- 请求涉及多个组件或服务
- 变更跨越多个用户触点
- 业务逻辑复杂或有多个场景
- 需求存在用户故事可以澄清的歧义
- 实施影响多个用户旅程
- 变更具有重大业务影响或风险

**仅在以下情况跳过**（低优先级 - 简单情况）：
- 纯内部重构且对用户零影响
- 范围清晰、隔离的简单缺陷修复
- 无用户可见影响的基础设施变更
- 无功能变更的技术债务清理
- 开发工具或构建流程改进
- 仅文档更新

**评估标准**：有疑问时，倾向于包含用户故事，用于：
- 涉及业务利益相关者参与的请求
- 需要用户验收测试的变更
- 有多种实施方案的功能
- 受益于团队共同理解的工作
- 需求清晰度有价值的项目

**评估流程**：
1. 分析请求的复杂度和范围
2. 识别用户影响（直接或间接）
3. 评估业务背景和利益相关者需求
4. 考虑团队协作收益
5. 边缘情况默认包含

**注意**：如果已执行需求分析，用户故事可以引用并基于这些需求。

**用户故事在一个子阶段内包含两个部分**：
1. **第 1 部分 - 规划**：创建含问题的故事计划，收集答案，分析歧义，获得批准
2. **第 2 部分 - 生成**：执行已批准的计划以生成故事和用户画像

**执行**：
1. **强制要求**：在 audit.md 中记录此阶段期间的任何用户输入
2. 从 `references/inception/user-stories.md` 加载所有步骤
3. **强制要求**：执行智能评估（user-stories.md 中的第 1 步）以验证用户故事是否必要
4. 加载逆向工程制品（如果是 brownfield）
5. 如果存在需求，创建故事时引用这些需求
6. 以适当的深度执行（最小化/标准/全面）
7. **第 1 部分 - 规划**：创建含问题的故事计划，等待用户回答，分析歧义，获得批准
8. **第 2 部分 - 生成**：执行已批准的计划以生成故事和用户画像
9. **等待明确批准**：遵循 user-stories.md 详细步骤中的批准格式 - 在用户确认之前不要继续
10. **强制要求**：在 audit.md 中记录用户的响应，包含完整的原始输入

# 🟢 CONSTRUCTION 阶段

**目的**：详细设计、NFR 实施和代码生成

**焦点**：确定如何构建（HOW）

**CONSTRUCTION 阶段中的子阶段**：
- 按单元循环（为每个单元执行）：
  - 功能设计（有条件执行，按单元）
  - NFR 需求（有条件执行，按单元）
  - NFR 设计（有条件执行，按单元）
  - 基础设施设计（有条件执行，按单元）
  - 代码生成（始终执行，按单元）
- 构建与测试（始终执行 - 在所有单元完成后）

**注意**：每个单元在进入下一个单元前完整完成（设计 + 代码）。

---

## 按单元循环（为每个单元执行）

**对于每个工作单元，按顺序执行以下子阶段：**

### 功能设计（有条件执行，按单元）

**执行条件**：
- 新的数据模型或模式
- 复杂的业务逻辑
- 业务规则需要详细设计

**跳过条件**：
- 简单的逻辑变更
- 没有新的业务逻辑

**执行**：
1. **强制要求**：在 audit.md 中记录此子阶段期间的任何用户输入
2. 从 `references/construction/functional-design.md` 加载所有步骤
3. 为该单元执行功能设计
4. **强制要求**：呈现 functional-design.md 中定义的标准双选项完成消息 - 不要使用新兴的三选项行为
5. **等待明确批准**：用户必须在"请求变更"或"继续下一子阶段"之间选择 - 在用户确认之前不要继续
6. **强制要求**：在 audit.md 中记录用户的响应，包含完整的原始输入

## 关键原则

- **自适应执行**：仅执行能增值的子阶段
- **透明规划**：始终在开始前显示执行计划
- **用户控制**：用户可以请求包含/排除子阶段
- **进度跟踪**：使用已执行和已跳过的子阶段更新 aidlc-state.md
- **完整审计追踪**：在 audit.md 中记录所有用户输入和 AI 响应并带时间戳
  - **关键**：准确捕获用户的完整原始输入
  - **关键**：切勿在审计日志中总结或改写用户输入
  - **关键**：记录每次交互，而不仅仅是批准
- **质量优先**：复杂变更获得完整处理，简单变更保持高效
- **内容验证**：根据 content-validation.md 的规则，始终在创建文件前验证内容
- **禁止新兴行为**：CONSTRUCTION 阶段的子阶段必须使用各自规则文件中定义的标准双选项完成消息。不要创建三选项菜单或其他新兴导航模式。

## 强制要求：计划级复选框执行

### 计划执行的强制规则
1. **绝不**在不更新计划复选框的情况下完成任何工作
2. **立即**在完成计划文件中任何步骤后，将该步骤标记为 [x]
3. **必须在完成工作的同一交互中完成**此操作

- **子阶段级**：在 aidlc-state.md 中跟踪整体工作流进度
- **立即更新**：所有进度更新必须在完成工作的同一交互中完成

## 提示日志记录要求
- **强制要求**：在 audit.md 中记录每次用户输入（提示、问题、响应）并带时间戳
- **强制要求**：准确捕获用户的完整原始输入（绝不总结）

- **关键**：始终向 EDIT audit.md 文件追加变更，切勿使用完全覆盖其内容的工具和命令
